# Report
|Num|Vulnerability|OWASP|Severity|What This Means|How We Fixed It|
|---|---|---|---|---|---|
|1|Anyone could approve a payout and pretend to be someone else|A01 - Broken Access Control|High|The "approve payment" feature didn't check who was actually asking. Anyone using it could approve money transfers and put any name down as the approver.|Now the system checks that the person is logged in, has permission to approve payments, and is only approving as themselves - not someone else.|
|2|The payment webhook accepted fake messages from anyone|A01 - Broken Access Control|Critical|A "webhook" is a message the bank sends to tell us a payment went through. Our system accepted these messages from anyone, not just the real bank, so an attacker could fake a message saying a payment was completed when it wasn't. It also had a bug that would crash the app the moment a real message arrived.|The system now checks a secret signature to confirm the message really came from the bank, ignores repeated/duplicate messages, and the crash bug was fixed.|
|3|Payment status could be set to anything, in any order|A03 - Injection / A04 - Insecure Design|Medium|A payment's status (like "Pending" or "Paid") was just free text, so it could be set to nonsense values, or skipped straight to "Paid" without ever being approved.|We now only allow a fixed list of valid statuses, and payments must move through the correct steps in order (Pending, then Approved, then Paid, then Settled).|
|4|Money amounts were stored in a way that can lose accuracy|A04 - Insecure Design|Medium|The amount of money in each payment was stored using a number format that computers can round incorrectly for money (similar to how 10 cents plus 20 cents can come out as 30.000000004 cents instead of exactly 30). Over time this can cause small but real accounting errors.|We switched to a number format built specifically for money, so amounts always add up exactly right.|
|5|Failed bank transfers were still marked as "Paid"|A04 - Insecure Design|Critical|If a transfer to the bank failed for any reason, the system still recorded the payment as successfully paid. This means a merchant could be told they were paid when they actually received nothing, with no record of the failure.|Now a payment is only marked "Paid" if the bank transfer actually succeeds. Failed transfers stay pending so they get retried, and the failure gets logged.|
|6|Anyone could look up any merchant's payment details|A01 - Broken Access Control|High|The page that shows payment details didn't check whether the person asking actually owned that payment. Anyone could guess a payment number and see another merchant's private financial information.|The system now checks that the payment belongs to the person asking before showing any details.|
|7|No record was kept of who did what|A09 - Logging & Monitoring Failures|Medium|None of the important actions (approving payments, receiving bank messages, status changes) were being written down anywhere. If money went missing or something suspicious happened, there would be no way to investigate what happened.|We added a logging system that records every important action - who approved what, when, and any failed or suspicious attempts - so problems can be traced later.|
|8|Error messages didn't explain what actually went wrong|A05 - Security Misconfiguration|Low|When something went wrong, the system just said "error" without saying whether it was a permissions problem, a missing record, or bad input. This makes it hard to tell a real security problem from a simple mistake.|We created clear, specific error types (e.g. "not allowed" vs "invalid status" vs "not found") so problems are easier to identify and review.|
